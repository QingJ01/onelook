# Spike 对比：core 与 mathlib 目标

| 指标 | `Nat.add_comm` | `List.length_append` | `List.map_comp_map` | `Filter.coext` |
|:---|---:|---:|---:|---:|
| 全闭包节点 | 47 | 77 | 649 | 1327 |
| 聚焦节点 | 47 | 77 | 50 | 50 |
| 全闭包边 | 241 | 366 | 6217 | 14332 |
| 聚焦边 | 241 | 366 | 233 | 207 |
| 类型级闭包 | 9 | 16 | 5 | 12 |
| 证明层新增 | 38 | 61 | 644 | 1315 |
| 聚焦内部管道 | 20 | 25 | 10 | 8 |
| 聚焦语义概念 | 3 | 6 | 9 | 8 |
| 聚焦语义 doc 覆盖 | 16/27 | 33/52 | 29/40 | 19/42 |
| 目标 docstring | 无 | 无 | 有 | 有 |

## 观察

- 两个 core 目标很小，全闭包即可读；mathlib 目标全闭包 649 节点，但半径 2 内只有 50 个节点，说明**聚焦半径是必需的**，全闭包不是教学视图。
- mathlib 目标自身有 docstring，1 跳 23 个节点里 18 个有文档；core 两个目标自身没有 docstring，文档覆盖率不足。
- mathlib 目标半径 2 内的 50 个节点被压成 9 个语义概念；聚焦后内部管道比例约 20%，比全闭包的 26% 更低，但仍然需要折叠。
- 全闭包膨胀主要来自 `ext`/simp 引入的 `getElem?`、除法、实例链等高阶管道；这些不是学习“map 复合”需要先懂的概念。
- 把 `inst*` 从概念锚点中剥开后，Filter 的 Set 概念从 16 个锚点降到 8 个，List 从 9 降到 7；实例机器单独成层。说明“概念 / 实例 / 内部管道”必须三层分开。
- Filter.coext 的聚焦语义 docstring 覆盖只有 19/42（45%），明显低于 List.map_comp_map 的 29/40（72%）；文档密度是领域相关的，不能假设 mathlib 处处有解释。
- 跨领域后必须手工补 Filter / Set / BooleanAlgebra 等规则，说明前缀式概念规则不可扩展；下一轮需要半自动聚类。

## 结论

管线在 core 和 mathlib 规模上都可用，但正确的产品视图是“目标邻域 + 概念/实例/机器分层 + 按需展开”，不是把依赖闭包整张画出来。下一轮应做：概念层半自动化、补 instance/simp/extends 边、以及真实学习任务评估。
